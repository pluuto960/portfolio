The Mirage

First blood 33 solves (All) 1 solve (No-LLM)

Archmage Mārtiņš cast a spell to hide his secret from prying eyes. To do so, he used a community spellbook that just so happened to have exactly what he needed. But is everything as it seems?

nc {IP} 1337

Introduction

Full disclosure

Before you read on, I need to come clean: I partly used AI to solve this challenge, and that is probably part of the reason I got first blood. I'm not going to pretend otherwise.

This one lived up to its name. The whole challenge is built around making you trust something you absolutely should not, and the title the mirage is basically the organizers telling you to your face that something here isn't real. It ended the event with 34 solves, which I think says less about the difficulty of the final exploit and more about how long it takes to stop trusting the thing you're supposed to distrust.

You get a mirage.zip with the service source and, promisingly, a flag.txt. That flag reads MCTF26{FAKE_FLAG_FOR_TESTING}. Clearly this wasnt the flag, so i dug deeper.

What's in the box

Unzipping gives a little container setup:

mirage/
├── Dockerfile / docker-compose.yml   # exposes :1337
├── launcher.c                        # reads /flag.txt onto FD 3, drops privs, execs qemu
├── main.c                            # the actual challenge binary (AArch64)
├── flag.txt                          # the decoy
└── qemu-aarch64-git/
    ├── PKGBUILD                      # builds QEMU from source...
    └── a.1 … a.5                     # ...and applies five "encrypted" patches

Reading launcher.c and the Dockerfile, the flow is: socat accepts your connection, launcher reads the real /flag.txt into a pipe, hands it to the challenge on file descriptor 3, drops to an unprivileged user, and runs the challenge inside QEMU user-mode emulation. The flag never touches disk where we can reach it — it only exists on FD 3 of a process we don't control.

So the question becomes: what does the challenge do with it, and how do I make it talk?

main.c — a suspiciously nice crypto setup

main.c is short and reads like a textbook example, which is exactly what made me squint at it. It:

  1. Reads up to 128 bytes of the flag from FD 3.
  2. Builds a 256-bit XOR key from four reads of the AArch64 RNDR register — the hardware random number generator:
    c
    asm volatile("mrs %0, rndr\n\t" "cset %w1, ne" : "=r"(val), "=r"(ok) :: "cc");
  3. XOR-encrypts the flag with that key and stashes the ciphertext back on FD 3.
  4. mmaps an RWX page, prints shellcode:, reads my shellcode, and jumps to it.

So I get arbitrary AArch64 code execution, and the ciphertext is sitting right there on FD 3. The entire challenge collapses to one thing: recover those four RNDR values.

And here's where I almost closed the file. RNDR is a hardware CSPRNG. Four reads of it as a one-time-pad XOR key is, on real silicon, completely unbreakable. I spent a while convinced the crypto was a dead end and that the "real" bug had to be a memory corruption or a QEMU escape in main.c's shellcode handling. That was the rabbit hole.

The realization

Then I remembered the title. Mirage. And I remembered that this binary doesn't run on real silicon — it runs under a QEMU that the challenge builds itself, from that PKGBUILD. Why ship your own QEMU unless you've done something to it?

The PKGBUILD builds upstream QEMU at a pinned commit, but before building it applies five patches that are "encrypted" — and it decrypts them with a repeating-key XOR, using a key that is written directly in the build script:

bash
xortool-xor -f "$patch_file" -r 'intruderalertredspyisinthebase' | git apply -

That's the whole mirage: a community "spellbook" (an AUR-style package) that looks legit, obfuscated just enough to feel safe, hiding a backdoor whose key is printed two lines above it. Decrypting a.1–a.5 (byte ^ key[i % len(key)]) gives a patch to target/arm/helper.c — specifically the implementation of the RNDR register:

c
static uint64_t getrand(RNGState *state) {
    if (rng_is_zero(state)) seed_rng(state);        // seeded ONCE per process
    uint64_t *s = state->s;
    const uint64_t result = rol64(s[1] * 5, 7) * 9; // xoshiro256** scrambler
    const uint64_t t = s[1] << 17;
    s[2]^=s[0]; s[3]^=s[1]; s[1]^=s[2]; s[0]^=s[3]; s[2]^=t; s[3]=rol64(s[3],45);
    return result;
}
// rndr_readfn now just: return getrand(&rngState);

So the "hardware RNG" is actually xoshiro256**, seeded once and advanced on every read. It's a great PRNG — fast, high quality — but it is emphatically not cryptographic. Two facts end the challenge:

  • The key words are just PRNG outputs #1–#4 of a single, shared stream.
  • xoshiro256** is fully invertible — both its state transition and its ** output scrambler. If I can see later outputs, I can roll the state backwards and reconstruct the earlier ones.

Making it talk

After setup() returns and I get control, the PRNG sits right before output #5. The key was outputs #1–#4. So the plan writes itself:

My shellcode:

  1. read(3, buf, 128) — grab the ciphertext.
  2. Read RNDR four more times — outputs #5–#8.
  3. write(1, buf, 160) — hand me the ciphertext plus those four values.

In AArch64 (RNDR is system register S3_3_C2_C4_0; syscalls read=63, write=64, exit=93), hand-assembled and sanity-checked with capstone:

asm
    sub  sp, sp, #256
    add  x19, sp, #0
    mov x0,#3 ; mov x1,x19 ; mov x2,#128 ; mov x8,#63 ; svc #0   ; read(3, buf, 128)
    mrs x9, rndr ; str x9, [x19,#128]                            ; outputs #5..#8
    mrs x9, rndr ; str x9, [x19,#136]
    mrs x9, rndr ; str x9, [x19,#144]
    mrs x9, rndr ; str x9, [x19,#152]
    mov x0,#1 ; mov x1,x19 ; mov x2,#160 ; mov x8,#64 ; svc #0   ; write(1, buf, 160)
    mov x0,#0 ; mov x8,#93 ; svc #0                              ; exit(0)

Now the offline math. One xoshiro output only leaks a scrambled s[1], so one value isn't enough — but the *5 and *9 are invertible mod 2⁶⁴, so I can unscramble each output back to the s[1] it came from, and four consecutive outputs pin down the entire 256-bit state (I let z3 finish it off):

python
inv9 = pow(9,-1,1<<64); inv5 = pow(5,-1,1<<64)
def unscramble(out):                       # rol(s1*5,7)*9  ->  s1
    return (rol((out*inv9) & M, 64-7) * inv5) & M

Then I invert the state transition to walk backwards. The only non-linear-looking step is o1 ^ (o1<<17), which you can peel off bit by bit from the low end:

python
def prev(s):
    a = list(s); a[3] = rol(a[3], 64-45)
    n3, n0, n1, n2b = a[3], a[0], a[1], a[2]
    o0  = n0 ^ n3
    rhs = n1 ^ n2b
    o1 = 0
    for bit in range(64):
        o1 |= ((((rhs>>bit)&1) ^ (((o1<<17)>>bit)&1)) << bit)
    o1 &= M
    o3 = n3 ^ o1
    o2 = (n2b ^ o0 ^ ((o1<<17) & M)) & M
    return [o0, o1, o2, o3]

Put it together: recover the state before output #5, roll it back four steps to the state before output #1, regenerate outputs #1–#4, and that's the key. Lay the key out the same way main.c did — a uint64_t key[4] reused as little-endian bytes, indexed i % 32 — and XOR:

python
B5  = solve_state_from_outputs(outputs_5_to_8)   # z3
B1  = B5
for _ in range(4): B1 = prev(B1)
key = [nxt(B1) for _ in range(4)]
kb  = b''.join(struct.pack('<Q', k) for k in key)
flag = bytes(ct[i] ^ kb[i % 32] for i in range(len(ct)))

The flag

MCTF26{cn_4pt_do3sn7_h4v3_5h1t_0n_m4rt1n5_ap7}

I ran it against two fresh connections — different seed, different ciphertext, different RNDR values each time — and both decrypted cleanly to the same string, so it's the method and not luck.

Closing thoughts

The actual exploit is maybe thirty lines of shellcode and some modular arithmetic. The hard part was emotional: you have to be willing to distrust a RNDR instruction, which every instinct says is the one thing in the room you can trust. The organizers knew that, named the challenge after it.

Two lessons worth keeping:

  • Read what your "community spellbook" actually applies. A legit-looking PKGBUILD with lightly obfuscated patches is a perfect place to hide a backdoor — especially one whose key is sitting in the same file.
  • xoshiro256** is not a CSPRNG. It's fast and statistically excellent, but it's invertible in both directions; a handful of observed outputs give you the whole stream, past and future.
